# Catalogue et administration Firebase

Cette application statique fournit le catalogue public des formations à la page `index.html` et l'interface d'administration à `admin.html`. Le catalogue public s'abonne en temps réel aux collections Firestore `trainings`, `announcements`, `trainingCategories`, `importantInformation` et `importantInformationCategories` ; les créations, modifications, suppressions et changements d'ordre enregistrés par l'administration sont ainsi reflétés automatiquement sur l'index ouvert. L'administration permet à l'administrateur connecté de gérer ces données. Sur le catalogue, les formations sont rangées par catégorie, présentées en cartes et ouvrent une fenêtre détaillée avec leur descriptif, leurs prérequis, leurs observations, leurs sessions et leur contact. En bas du catalogue, les dates et informations importantes sont regroupées par catégorie. Le catalogue ne crée pas de compte et n'importe pas automatiquement `firestore_export.json`.

## Configuration Firebase

1. Dans la console Firebase du projet `seec-2da03`, ajoutez une **application Web** au projet. La configuration Android de `google-services.json` ne remplace pas la configuration Web.
2. Copiez les valeurs de configuration Web dans `firebase-config.js` (`apiKey`, `authDomain`, `projectId`, `storageBucket`, `messagingSenderId` et `appId`).
3. Dans **Authentication > Sign-in method**, activez le fournisseur **E-mail/Mot de passe**. Créez le compte administrateur et vérifiez son adresse e-mail.
4. L'accès administrateur exige une adresse e-mail vérifiée autorisée dans `app.js`, `firestore.rules` et le Worker Cloudflare. Pour ajouter ou retirer un compte, suivez le mode d'emploi `ajouter-administrateur.txt` ; il couvre également l'autorisation d'envoyer des notifications.
5. Publiez les règles dans **Firestore Database > Règles**. Elles réservent les collections gérées aux administrateurs vérifiés autorisés ; tout le reste est refusé. Après toute modification des règles, déployez-les avec `firebase deploy --only firestore:rules --project seec-2da03`.
6. Configurez et déployez le Worker Cloudflare avec le code `cloudflare-worker.js` et les paramètres décrits dans `cloudflare-notifications-procedure.txt`. Le Worker vérifie le jeton Firebase de l'administrateur puis envoie les nouvelles annonces ou une notification ponctuelle rédigée dans l’onglet **Annonces & Notifications** via FCM HTTP v1. La variable Cloudflare `ADMIN_EMAILS` accepte une liste d'adresses autorisées séparées par des virgules. Une notification ponctuelle n'est pas ajoutée aux annonces Firestore. L'administration indique si FCM accepte l'envoi, mais FCM ne fournit pas le nombre d'appareils destinataires. Aucun historique des notifications ponctuelles n'est conservé. Les messages FCM Android sont des messages de données affichés par le service de l'application, avec le logo en grande icône et une icône monochrome dans la barre d'état. Aucune Cloud Function Firebase n'est requise pour cet envoi.
7. Le calendrier des agents lit les flux ICS via le Worker Cloudflare déjà utilisé pour les notifications ; les occupations sont traitées à la demande dans le navigateur et ne sont plus enregistrées dans Firestore. Aucune Cloud Function Firebase n'est nécessaire. Pour publier cette modification, déployez les règles et l'hébergement avec `firebase deploy --only firestore:rules,hosting --project seec-2da03`. Ces services peuvent rester sur le forfait Spark. Le Worker Cloudflare existant fournit déjà la lecture des calendriers ; il n'a pas besoin d'être modifié pour cette évolution. En local, servez les pages en HTTP avec `python -m http.server 8000` ; ne les ouvrez pas en `file://`.

## Environnement de test local isolé

L’application bascule automatiquement sur les émulateurs Firebase lorsque son origine est `localhost` ou `127.0.0.1`. Elle utilise alors le projet fictif `demo-formation-local`, affiche un bandeau rouge de test et ne se connecte pas au projet de production. Les services externes Cloudflare/FCM (notifications et synchronisation AGATT) sont désactivés dans ce mode. N’ouvrez pas l’application avec une autre adresse locale si vous souhaitez être certain d’utiliser l’environnement émulateur.

Prérequis : Firebase CLI (`firebase --version`), Java 21 ou ultérieur et Node.js. Le projet déclare Node.js 22 pour les fonctions; si une autre version est installée, Firebase CLI peut afficher un avertissement et utiliser la version disponible.

Depuis la racine du projet, démarrez les émulateurs (la première fois, le téléchargement des émulateurs peut prendre quelques minutes) :

```powershell
firebase emulators:start --config firebase.test.json --project demo-formation-local --only auth,firestore,functions,hosting --export-on-exit .firebase/local-emulator-data
```

Ouvrez ensuite :

- Catalogue : `http://127.0.0.1:5000/`
- Administration : `http://127.0.0.1:5000/admin.html`
- Calendrier : `http://127.0.0.1:5000/calendrier.html`
- Interface des émulateurs : `http://127.0.0.1:4000/`

Les émulateurs sont vides au premier démarrage. Dans l’interface des émulateurs, créez un utilisateur de test avec l’adresse administrateur autorisée par les règles, marquez son adresse comme vérifiée, puis connectez-vous à l’administration. Ce compte n’existe que dans l’émulateur. Créez ensuite des catégories, formations et dates de test depuis l’administration pour vérifier l’affichage public, le calendrier et les statistiques. N’importez pas `firestore_export.json` : il ne faut pas utiliser des données de production comme jeu de test.

À l’arrêt avec `Ctrl+C`, les données de l’émulateur sont exportées dans `.firebase/local-emulator-data/`. Les démarrages suivants peuvent les recharger ainsi :

```powershell
firebase emulators:start --config firebase.test.json --project demo-formation-local --only auth,firestore,functions,hosting --import .firebase/local-emulator-data --export-on-exit .firebase/local-emulator-data
```

Ces données locales sont ignorées par Git. Pour repartir d’un environnement vide, arrêter d’abord les émulateurs, puis supprimer uniquement le dossier `.firebase/local-emulator-data/`. Ne lancez pas `firebase deploy` pour démarrer ou tester cet environnement : cette commande publie vers Firebase et n’est pas nécessaire ici. Les tests locaux ne vérifient pas l’intégration réelle avec Cloudflare, FCM ou AGATT.

## Versions et relecture annuelle

La création et le suivi des versions se font sur la page dédiée **Versions et relecture**, accessible depuis la barre de compte de l’administration (`admin-versions.html`). Cette page est séparée des onglets habituels. Pour le pas-à-pas, voir [TUTO-RELECTURE-CATALOGUE.md](./TUTO-RELECTURE-CATALOGUE.md).

Un administrateur crée une copie du catalogue courant lorsqu’une relecture est nécessaire. Le numéro d’année et le nom de version sont à renseigner. Cette copie est isolée : les ajouts ou modifications réalisés dans l’administration habituelle continuent de modifier le catalogue public et ne sont pas inclus dans la copie après sa création. Le bouton **Modifier cette copie** ouvre un mode d’édition isolé qui ne propose que la gestion des formations, des dates à retenir et des paramètres du catalogue (catégories, lieux et contacts), sans exposer les autres sections de l’administration.

Le lien sécurisé de relecture apparaît une seule fois après la création. Copiez-le et transmettez-le aux relecteurs par le canal de votre choix ; aucun compte de relecteur n’est nécessaire. Le lien permet de consulter la copie et de l’approuver ou de demander des corrections. Après une demande de corrections, les administrateurs peuvent modifier la copie puis la soumettre de nouveau. Un lien peut être révoqué et remplacé depuis la gestion de version. La relecture est désactivée après publication.

Une version qui n’a pas été publiée peut être supprimée depuis sa carte, quel que soit son état (brouillon, en relecture, approuvée ou à corriger). Sa copie et son lien sont supprimés sans modifier le catalogue public ni les archives. Cette suppression est définitive ; si elle est interrompue, relancez-la depuis la carte indiquant **Suppression en cours**. Les versions publiées ne sont pas supprimables par cette action.

Seule une version approuvée peut être publiée. La publication remplace le catalogue public en une seule opération atomique et archive le catalogue précédent ; les données de l’ancienne version ne sont donc plus publiées, mais restent disponibles pour restauration depuis **Archives des catalogues remplacés**. Une restauration remet l’archive en ligne et conserve les modifications postérieures non conflictuelles lorsqu’elles peuvent être détectées. Vérifiez le catalogue après restauration. Les ajouts en cours d’année qui ne nécessitent pas de relecture peuvent toujours être effectués directement dans l’administration.

Dans **Statistiques**, le sélecteur **Année** permet de consulter une année précise ou **Toutes les années**. Une session couvrant plusieurs années contribue aux statistiques de chacune des années qu’elle chevauche.

## Sauvegarde et restauration Firestore (forfait Spark)

Le script local `functions/scripts/firestore-backup.js` permet de sauvegarder et restaurer Firestore sans Cloud Functions ni sauvegarde gérée payante. Il utilise l’Admin SDK et les identifiants Application Default Credentials de Google Cloud. Installez les dépendances depuis la racine du projet avec `npm --prefix functions install`, puis connectez le compte Google autorisé à administrer Firestore :

```powershell
gcloud auth application-default login
```

Pour un usage plus simple sous Windows, lancez par double-clic `functions/scripts/Sauvegarde-restauration-Firestore.cmd`. Le menu propose la sauvegarde, l’aperçu d’une restauration et la restauration confirmée. Il demande l’identifiant du projet, permet de choisir le fichier JSON avec une fenêtre de sélection et réutilise le script de sauvegarde existant. Si `gcloud` ou les identifiants ADC ne sont pas disponibles, il peut utiliser temporairement le chemin d’une clé JSON de compte de service; la clé n’est ni copiée ni enregistrée par le lanceur. Gardez cette clé privée et préférez ADC quand Google Cloud CLI est disponible. Les deux fichiers du lanceur sont dans `functions/scripts`, dossier exclu de l’hébergement Firebase.

Les sauvegardes par défaut sont créées hors du dépôt, dans `%USERPROFILE%\Documents\FirestoreBackups\<projectId>\`. Il est également possible de préciser `--file` avec un chemin situé hors du dépôt. Gardez une copie chiffrée supplémentaire sur un support séparé.

Depuis la racine du projet, créez une sauvegarde en remplaçant `<projectId>` par l’identifiant exact du projet Firebase :

```powershell
npm --prefix functions run firestore-backup -- backup --project <projectId>
```

Pour simuler une restauration sans modifier la base :

```powershell
npm --prefix functions run firestore-backup -- restore --project <projectId> --file "C:\chemin\vers\la-sauvegarde.json"
```

Une restauration complète est destructive : elle remplace les documents couverts par la sauvegarde et supprime les documents actuellement présents qui n’y figurent pas. Avant de l’appliquer, arrêtez les modifications du catalogue, vérifiez l’identifiant du projet et le nombre d’opérations affiché. Pour l’appliquer, ajoutez `--apply` à la commande ; le script crée d’abord une sauvegarde de sécurité de l’état courant, puis exige la confirmation exacte `RESTORE <projectId>`. La restauration est limitée à 18 000 écritures/suppressions afin de préserver une marge sur le quota journalier gratuit ; vérifiez aussi la consommation réelle du projet avant de la lancer.

Le fichier de sauvegarde est contrôlé par SHA-256 et la restauration conserve les types Firestore pris en charge par le script. Les sous-collections sont parcourues depuis leurs documents parents existants ; Firestore autorise des sous-collections orphelines sous des documents supprimés, que l’énumération standard de l’Admin SDK ne permet pas de découvrir sans connaître leurs chemins. Cette situation ne doit pas être considérée comme couverte par une sauvegarde locale. Le script ne doit pas être utilisé pour tester sur un projet réel : utilisez l’émulateur et le projet `demo-formation-local`.

Le déploiement Spark de l’application reste limité à l’hébergement et aux règles Firestore ; n’incluez pas `functions` dans la commande de déploiement :

```powershell
firebase deploy --only firestore:rules,hosting --project <projectId>
```

La racine (`index.html`) est le catalogue public ; sur ordinateur, le bouton **Imprimer / Exporter en PDF**, dans l’en-tête, ouvre la boîte d’impression du navigateur, où choisir **Enregistrer au format PDF**. L’export comprend les formations publiées, une page de garde par catégorie, une fiche par formation (qui peut continuer sur la page suivante si son contenu est long), puis les dates et informations à retenir. Les fiches utilisent des colonnes compactes pour les prérequis, sessions et phases ; les observations et le contact restent sur la largeur entière, le contact venant en dernier. Les couvertures affichent le logo SDIS 53, le nom de la catégorie puis « Programme de formation ». Un pied de page commun indique SDIS 53, le catalogue et le numéro de chaque page. Le format est A4 ; activez l’impression des arrière-plans pour préserver au mieux les couleurs et désactivez les en-têtes/pieds de page du navigateur pour éviter les doublons. `calendrier.html` affiche les sessions datées sous forme de calendrier mensuel sur ordinateur et de liste chronologique sur téléphone. Utilisez le sélecteur de mois ou les flèches pour naviguer ; les sessions qui se chevauchent respectent l'ordre des catégories et des formations du catalogue. Pour une session de plusieurs jours, le calendrier affiche la formation sur chaque journée avec le repère J1, J2, J3, etc., y compris dans la liste mobile. Survolez ou sélectionnez au clavier une session pour afficher ses informations détaillées. Dans l’administration, l’onglet **Calendrier** affiche les formations par jour et permet de filtrer par lieu. Une alerte signale, pour chaque lieu et chaque jour, plus de deux formations distinctes simultanées. L’onglet **Statistiques**, en dernière position, présente les formations, sessions et jours cumulés par domaine, ainsi que les jours d’utilisation par lieu. Le domaine correspond à la sous-catégorie si elle est renseignée, sinon à la catégorie ; les domaines de même nom sont regroupés même s’ils appartiennent à des catégories différentes. Les onglets **Paramétrage** et **Annonces & Notifications** regroupent respectivement les catégories/lieux/contacts et les annonces/notifications. **Dates à retenir** se trouve juste après **Formations**. En cliquant sur une session publique, la fiche complète de la formation s'ouvre. `admin.html` est l'interface de gestion. La page `agent-calendar.html` est réservée à `luc.cesbron@sdis53.fr` et propose trois onglets : la gestion (ajout, modification, suppression) de plus de 50 agents dans `agentCalendars`, un calendrier mensuel filtrable par type **Incendie**, **Caisson** ou **Toutes**, et les statistiques annuelles par agent avec une année indépendante du mois affiché. Les occupations qui chevauchent deux années sont attribuées à l'année de leur date de début pour éviter de compter deux fois une même activité. Les fiches contiennent `firstName`, `lastName`, `status` (`SPP` ou `SPV`) et `icsUrl`. Les sigles **DS COEPT F1**, **FOR CAISSON**, **F2 FOR**, **F3 FOR**, **F4 FOR** et **F1 RP** sont classés Caisson ; **FOR INC** et **DS TC INC** sont classés Incendie ; **Assistant INC** et **Assistant COD** ont leur propre couleur et leur propre groupe statistique. Le filtre Incendie inclut les assistants. Les sigles sont reconnus comme des codes complets, sans confondre par exemple **Assistant COD** avec **Assistant CODIS** ou **F2 FOR** avec **F4 FOR**. Pour chaque groupe, les statistiques comptent les occupations **Validé** et **Disponible**. Les heures des occupations contenant **FOR** ou **F1 RP** valent 4 h 30 si l’occupation se termine à 12 h ou commence à 14 h, sinon 9 h ; celles contenant **DS** valent respectivement 5 h ou 10 h. Les assistants sans ces sigles gardent la durée issue du calendrier ICS. Pour les occupations Caisson **Validé**, les statistiques ajoutent le total de brûlages et le temps d’exposition : fin à 12 h = 2 brûlages et 40 minutes, sinon 3 brûlages et 1 heure. Chaque date du calendrier affiche aussi les compteurs d'occupations validées et disponibles. Les règles Firestore limitent l'accès à cette collection à l'adresse administrateur autorisée ; le Worker Cloudflare vérifie le jeton Firebase, n'accepte les flux que depuis `agatt.sdis53.fr` et les lit côté serveur. Les erreurs de lecture indiquent le statut AGATT ou l'échec de connexion au Worker sans exposer l'URL privée. Le fichier local `occupation.ics` sert d'exemple de format et n'est pas chargé par l'application. Le Worker Cloudflare doit être republié pour appliquer les règles horaires et de brûlages. Les quatre pages référencent le manifeste et enregistrent le service worker : l'application peut être installée depuis le catalogue, le calendrier public, l'administration ou la page des agents. Après déploiement HTTPS, utilisez **Installer l'application** dans le navigateur (ou **Ajouter à l'écran d'accueil** sur mobile) depuis l'une de ces pages. Le logo d'installation provient de `PWA.png` ; les icônes web 192 × 192 et 512 × 512 sont dans `icons/`.

Les occupations ICS sont lues à la demande depuis les flux AGATT et mises en cache uniquement en mémoire dans la page, pour éviter de relire les flux pendant 24 heures. Elles ne sont pas écrites dans Firestore et ce cache est perdu à la fermeture de la page. **Actualiser les flux ICS** force une nouvelle lecture. Le calendrier affiche les événements renvoyés par le flux pour le mois sélectionné, et les statistiques annuelles sont calculées à partir des événements actuellement disponibles dans les flux ; les occupations passées retirées d’AGATT ne sont donc plus disponibles pour les statistiques. La page accepte plus de 50 agents et répartit les requêtes Worker en lots de 50 calendriers maximum. Les anciennes occupations déjà enregistrées dans `agentOccupations` et les anciens marqueurs `agentCalendarSync` ne sont pas supprimés automatiquement : les règles interdisent désormais leur création ou modification, mais autorisent encore leur suppression (notamment lors de la suppression d’un agent). Ces anciens documents restent inclus dans les sauvegardes tant qu’ils n’ont pas été supprimés.

La PWA met en cache les ressources statiques pour ouvrir le shell de l'application hors connexion. À l'ouverture, au retour dans l'application et toutes les cinq minutes, elle vérifie si une nouvelle version est déployée ; elle l'active puis recharge automatiquement la page. Les pages, scripts et styles ne sont pas conservés dans le cache HTTP du navigateur, tandis que le service worker conserve une copie utilisable hors connexion. La mise à jour nécessite une connexion et sera appliquée dès la prochaine vérification. La connexion et les données Firebase nécessitent toujours une connexion Internet.

La clé API Web Firebase est une configuration cliente, pas un mot de passe administrateur. La protection des données est assurée par les règles Firestore et l'authentification.

## Données

Les documents de formation sont enregistrés dans `trainings`, ceux d'annonce dans `announcements` et les catégories dans `trainingCategories`. Les lieux réutilisables sont enregistrés dans `trainingLocations` et les contacts dans `trainingContacts`. Dans l'onglet **Lieux et contacts**, créez, modifiez ou supprimez ces références ; un contact doit avoir un nom, tandis que son e-mail et son téléphone sont facultatifs. Les menus des sessions proposent les lieux enregistrés ; sans sélection, l'application mobile affiche « Lieu non renseigné ». Le menu Contact des formations propose les contacts enregistrés ; lors de la création ou modification d'une formation, ses coordonnées sont enregistrées directement dans `trainings.contactName`, `trainings.contactPhone` et `trainings.contactEmail` (chaque champ est une chaîne, vide si la donnée est absente). L'identifiant saisi d'une formation sert également d'identifiant de document Firestore.

Les catégories d’informations sont enregistrées dans `importantInformationCategories` (`name`, `order`, `color`) et les dates, textes et rappels dans `importantInformation` (`categoryId`, `title`, `type`, `description`, `dates`, `recurrence`, `published`, `order`). Dans l'onglet **Dates à retenir**, utilisez les poignées de déplacement pour ordonner les catégories et les informations à l’intérieur de leur catégorie ; l’ordre est enregistré dans Firestore. Choisissez la couleur de chaque catégorie dans la palette, ou avec le sélecteur de couleur. Chaque entrée de `dates` peut contenir une date ISO `YYYY-MM-DD`, un libellé et un lieu ; une date vide est affichée comme « À définir ». Décochez **Afficher sur le catalogue public** pour masquer un élément sans le supprimer. Les documents restent conservés dans Firestore, y compris les informations anciennes.

Dans l'onglet **Catégories**, utilisez les icônes pour créer, renommer ou supprimer une catégorie et gérer ses sous-catégories. Les actions « ajouter une sous-catégorie », « modifier » et « supprimer » de chaque catégorie sont placées sous son titre. Les formulaires de création et de modification d'une sous-catégorie permettent de modifier son nom et sa couleur. Choisissez la couleur d'une catégorie lors de sa création ou modification à partir de la palette standard ; une autre couleur peut être ajoutée à la palette persistée dans `trainingCategories/__settings__`, qui est également proposée pour les sous-catégories. La couleur choisie est enregistrée directement dans le document de la catégorie ou dans l'entrée correspondante de `subCategories`. Faites glisser les poignées pour ordonner les catégories et sous-catégories ; les positions sont enregistrées dans `trainingCategories.order` et dans le champ `order` de chaque entrée de `subCategories`. Renommer une catégorie ou une sous-catégorie met à jour les formations qui l'utilisent. La suppression est refusée tant qu'une formation utilise cette valeur : modifiez d'abord les formations concernées.

Dans l'onglet **Formations**, chaque catégorie est présentée en accordéon (une seule peut être dépliée à la fois). Les formations sont ordonnées par glisser-déposer dans toute leur catégorie, indépendamment de leur sous-catégorie ; celle-ci est affichée près du titre. Leur ordre est enregistré dans `trainings.order` et respecté par l'application Android. Les catégories et sous-catégories déjà présentes dans les formations existantes sont également proposées, même avant d'être enregistrées dans le catalogue. Les sous-catégories anciennes, stockées sous forme de texte, restent prises en charge ; elles reçoivent une couleur et un ordre par défaut jusqu'à leur enregistrement suivant.

Les collections Firestore n'ont pas besoin d'être créées manuellement : elles apparaissent dans la console après l'enregistrement de leur premier document. Si le compte n'a pas encore vérifié son adresse, l'application propose de renvoyer le courriel de vérification ; ouvrez le lien reçu, puis déconnectez-vous et reconnectez-vous.

L’onglet **Paramétrage** permet d’activer le mode maintenance des pages publiques avec un bouton bascule et une confirmation modale. Le réglage est enregistré dans `siteSettings/public` ; les pages `index.html` et `calendrier.html` masquent leur contenu et affichent un message avec un lien vers l’administration, tandis que `admin.html` reste accessible. Les règles Firestore autorisent la lecture publique de ce seul document et réservent sa modification aux administrateurs. Si le réglage ne peut pas être vérifié, les pages publiques restent masquées et affichent un message de service temporairement indisponible.

Dans la liste des formations de l’administration, le bouton œil permet de masquer une formation ou de la rendre de nouveau visible ; une modale demande confirmation. Les formations masquées restent gérables dans l’administration, mais disparaissent du catalogue et du calendrier publics. Les formations existantes restent visibles par défaut.

Les sessions sont triées par date chronologique dans le formulaire et les calendriers. Le bouton d’annulation d’une session ouvre une confirmation avec saisie obligatoire du motif. Une session annulée reste affichée avec son état et son motif dans le catalogue, la fiche formation et les calendriers ; elle n’est plus prise en compte dans les statistiques et alertes de surcharge des lieux.

Lorsqu'une nouvelle annonce est créée depuis l'interface, son identifiant numérique est incrémenté automatiquement à partir des annonces existantes et sa date est définie à la date du jour ; lors d'une modification, la date est actualisée automatiquement. Le type est choisi parmi `AJOUT`, `ANNULATION` et `MODIFICATION` ; les anciennes valeurs sont traduites dans l'interface et restent compatibles avec Android. Une nouvelle annonce appelle le Worker Cloudflare à `https://wild-sky-abe4.cesbronluc.workers.dev/`, qui vérifie le jeton Firebase de l'administrateur et envoie une notification FCM au sujet `announcements`. Le titre de la notification reprend le titre de l'annonce, et son corps reprend son message. La modification d'une annonce existante n'envoie pas de notification. L'application Android s'abonne à ce sujet au démarrage ; le catalogue PWA ne s'y abonne pas. Le Worker et ses secrets doivent être déployés et configurés dans Cloudflare avant l'envoi réel.

Les sessions peuvent être saisies directement dans une formation, sans phase ; leur nom est facultatif. Pour les formations structurées, ajoutez des phases et leurs sessions. Chaque session peut avoir une date de début, une date de fin facultative et un lieu facultatif. Les sessions directes sont enregistrées dans `sessions`, celles d'une phase dans `phases[].sessions`. Les dates sont aussi conservées dans `dates` sous une forme lisible par l'application Android, avec `startDate` et `endDate` pour les dates choisies. Les anciennes dates textuelles restent affichées et conservées tant qu'elles ne sont pas remplacées avec le sélecteur.

Modifier l'identifiant d'un document le déplace vers un nouveau document puis supprime l'ancien. La suppression d'un document est définitive. Les règles contrôlent que l'identifiant stocké correspond à l'identifiant du document.

Dans la gestion du calendrier des agents, le formulaire d’ajout et de modification s’ouvre dans une fenêtre modale. Le profil enregistre le booléen `formateurCaisson`, modifiable avec le bouton bascule **Formateur caisson**. La liste répartit les agents en deux colonnes : **Formateurs caisson** pour ceux dont ce champ est activé, et **Formateurs incendie** pour tous les autres. Les règles Firestore autorisent ce champ booléen ; après leur mise à jour, republiez-les avec `firebase deploy --only firestore:rules --project seec-2da03` pour permettre les enregistrements.

Pour lancer rapidement l'interface, servez ce dossier par un serveur HTTP statique ou déployez-le sur Firebase Hosting. L'ouverture directe en `file://` n'est pas prise en charge.
